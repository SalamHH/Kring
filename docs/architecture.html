Kring architecture overview · 15 November 2026

How Kring works, from police log to phone

Kring turns the Norwegian police log into calm alerts for the places a person cares about. A worker reads Politiloggen every minute, places each incident on the map with an honest margin of error, and pushes only serious incidents inside a saved place. An API serves the Expo app on iOS and Android. Everything on the server is one Python codebase and one Postgres database on Render.

The big picture

The whole system on one page

Three things run on Render: a worker, an API and a database. Everything else is someone else's service, and all of it is free to use without a key.

Worker
The only part that talks to Politiloggen and sends pushes. One cycle every 60 seconds, and only one worker at a time.
API
The only part the app talks to, apart from map tiles. It keeps no state of its own; everything lives in Postgres.
Database
Public incidents on one side, devices and places on the other. PostGIS does the distance maths in metres.
App
Registers itself anonymously, shows places and incidents, and opens the right incident when a push is tapped.

What a deploy does

  1. PushRender sees a new commit on the deploy branch.
  2. Builduv sync --locked --no-dev in backend/.
  3. Migratealembic upgrade head. Both services run it; a lock lets only one migrate.
  4. StartA new API instance and a new worker start next to the old ones.
  5. CheckOnce /v1/health/live answers, traffic moves to the new API.
  6. Hand overThe new worker takes the lock when the old one stops.

Running it

  • Freshness. GET /v1/health returns 200 while the last successful poll is under 10 minutes old, and 503 after that. Render's own check uses /v1/health/live, so a Politiloggen outage doesn't restart the API.
  • Database access. Closed to the internet (ipAllowList: []), because places are personal data. To connect from a laptop, add your IP in the dashboard for a while, then remove it.
  • Secrets. None in the repo. The database URL comes from the Blueprint; an Expo access token, if it is ever needed, goes in the dashboard.
  • Rollback. Per service in the dashboard. Migrations so far only add things, so older code still runs on the newer schema.
  • Logs. One ingest LastDay line per cycle. An ERROR when no poll has worked for 10 minutes.

Backend

One codebase, two processes

The worker does everything that happens on a clock. The API does everything a person asks for. They never call each other; they share the database.

One worker cycle

A cycle starts every 60 seconds, counted from the start of the previous one. A slow cycle is followed at once by the next, never by two.

Ingest

transaction 1

  1. Fetch. The last day's threads, at least 3 pages of 100. After an outage of 23 hours or more, the last quarter.
  2. Filter. Keep Oslo and Akershus, plus police-district notices that cover them.
  3. Store. Upsert events and messages by thread id. Each thread in its own savepoint, so one bad thread can't sink the cycle.
  4. Geocode. New threads, changed areas, and anything still imprecise. Kartverket answers are cached.
  5. Classify. Planned control or not, severity, precision tier.
commit

Plan pushes

transaction 2

  1. Pick up. Every event with notified_at still empty, oldest first.
  2. Match. PostGIS finds places within reach; the push rules decide.
  3. Record. Insert one notifications row per push, then mark the event handled.
commit

Deliver

after both commits

  1. Send. To Expo in batches of up to 100; keep each ticket.
  2. Receipts. 15 minutes later, mark each push ok or failed. Drop tokens Expo reports as dead.

If the worker dies between steps 5 and 6, the next cycle picks the events up. Events it first sees more than 10 minutes after they were stored are marked handled without a push, so nothing stale goes out after an outage.

Placing an incident on the map

Police messages carry no coordinates, only a free-text area («Grünerløkka», «E6 Furuset») and the message itself. The geocoder tries each method in order, and the first one that works wins. Every result carries an uncertainty in metres. The logic is a port of research/presisjonstest.py.

Three precision tiers

Gatenivå

≤ 500 m

Street level. Counts for a place of any radius.

Nabolag

501–1 500 m

Neighbourhood. Counts only when the place's radius is 1 km or more.

Bydel

> 1 500 m, or no point

Never matches and never pushes. Listed as «imprecise nearby» when its circle overlaps the place.

Who gets a push

How calm is it?

A replay of 13 weeks of real Oslo and Akershus data: a 1 km Hjem place at Grünerløkka would have had 9 pushes, about 0.7 a week. A Skole place at Tøyen skole had 15 severe matches but only 3 pushes, because most fell outside weekdays 08–16. The beta target is 0.5–2 a week.

The API

JSON over HTTPS. There are no accounts: on first launch the app registers and gets a random secret, which it sends as a bearer token. The server keeps only its SHA-256 hash.

Limits, kept in memory: 120 requests a minute per device, 30 searches a minute, 20 registrations an hour per IP, 10 places per device. Every error has the same shape: {"error": code, "message": text}.

Data

Eight tables, split in two

Personal data comes from phones. Public data comes from the police log. The two halves meet in one table, notifications, which records who was pushed about what.

The app

Three screens and no tab bar

What the app does on its own

  • First launch. Calls POST /v1/devices and stores the secret. It stays readable after the first unlock, so a push can be handled on a locked phone.
  • Every launch and every return to the foreground. Makes sure the device exists and sends the current push token. If the server has forgotten the device (a 401), it registers again, once.
  • No location. Places are points the person picks, never GPS. The location permissions MapLibre would add on Android are blocked in app.json.
  • Which server. EXPO_PUBLIC_API_URL if set, the local API in development, otherwise kring-api.onrender.com.

User flow

What a person does, and what happens underneath

A parent sets up their child's school and then mostly forgets about the app. That is the intended experience.

The personThe system
  1. Installs and opens Kring. There is nothing to sign up for. Allows notifications.
    POST /v1/devices returns a secret, stored on the phone. PUT /v1/devices/me sends the push token, platform and time zone.
  2. Taps «Legg til sted», searches «Tøyen sk», picks Tøyen skole and the Skole template, keeps 1 km.
    GET /v1/geocode/search asks Kartverket and ranks Oslo and Akershus first. The template sets Vold, Brann, Savnet and Ro og orden, weekdays 08–16.
  3. Sees what the place would have caught, for example 5 incidents in the last 30 days, and saves.
    GET /v1/preview counts real incidents. POST /v1/places stores the place and its municipality, and flags it if it is outside Oslo and Akershus.
  4. Gets on with life. Hjem says «Rolig siste 7 dager».
    GET /v1/places/{id}/events for each card. GET /v1/health for «Oppdatert for N minutter siden».
  5. A weekday morning, a push: «Brann ca. 150 m fra Skolen».
    The worker stored the incident, matched it to this place, ran the push rules and sent one push. The text uses only Kring's own fields.
  6. Taps it. Hendelse shows the map with its margin of error, how precise it is, «Hvorfor fikk jeg dette?» and every police update.
    GET /v1/events/{id}?place_id=… returns the whole thread and why it reached this place.
  7. Adjusts or leaves. «Færre slike varsler» opens the place's settings. Deleting everything is one tap (M2).
    PATCH /v1/places/{id}. DELETE /v1/devices/me removes the device, its places and its push history.

End to end

One incident, from police log to phone

Follow one fire in Hølandsgata through the system. The target is a push on the phone at most 2 minutes after the police publish.

Where the 2 minutes go

  • Waiting for the next poll: up to 60 seconds. The largest share, and fixed by the poll interval.
  • Processing: about a second per cycle once the geocode cache is warm.
  • Expo, Apple or Google, then the phone: usually seconds, and outside Kring's control.
  • Measured in step 13: on production for at least 2 days, split into police → stored (ingested_at) and stored → sent (sent_at).

Later police messages in the same thread update the stored event. Its placement may improve and Hendelse shows the new text, but the thread never pushes a second time.

Design choices

Kept simple on purpose

There is no job queue, no cache server, no scheduler and no user database. Postgres covers those jobs, which keeps the system to three moving parts that one person can run.

Postgres is the to-do list

notified_at IS NULL

The notifier works through events it hasn't handled yet. If the worker dies between storing and pushing, the next cycle carries on where it stopped.

One lock, one worker

pg_try_advisory_lock

A Postgres advisory lock lets only one worker poll. During a deploy the new worker waits for it. Nothing else coordinates them.

A row before every push

UNIQUE (place_id, event_id, kind)

The notifier writes the notification row first and sends second. A crash or a restart can't produce a second push for the same place and incident.

The cache is a table

geocode_cache

Kartverket answers are kept in Postgres, including a genuine «not found». Failures are never kept, so they are retried on the next cycle.

Geometry stays in SQL

ST_DWithin + GiST index

Matching is one indexed PostGIS query in metres. The same rule runs both ways: event to places for pushes, place to events for lists and the preview.

No accounts

POST /v1/devices

A device is a random 32-byte secret. Nothing to sign up for or reset, and one call erases everything about it.

Push text from Kring's own fields

notify/copy.py

A notification says what, how far, where and how precise. It never quotes the police, so names and descriptions of people can't reach a lock screen.

Poll at a steady pace

poll_interval_s = 60

Politiloggen offers no webhooks. One poll a minute uses at most half of the 2-minute budget, and the window widens by itself after an outage.

Known gaps

  • Push isn't live end to end yet. iOS needs an APNs key, which needs the paid Apple Developer membership. Android needs a Firebase project for FCM. Both are part of step 12.
  • One API instance. Rate limits live in memory and reset on each deploy, and the per-IP registration limit trusts X-Forwarded-For. Shared limits come in M4.
  • No weekly summary, settings or delete button yet. They are M2; digest/ is still empty.
  • Akershus is placed less precisely than Oslo. More incidents land at town level, and 14 % have no area at all. M3 works on this.
